# JevCompass roadmap

**Read by stage:** [current pilot evidence](PILOT.md) · [20-case design (not execution)](PILOT_CASES.md) · [release/task receipts](TASKS.md) · [quick start](README.md).

Published [v0.1.21](https://github.com/acidkill/JevCompass/releases/tag/v0.1.21) removes the false remote choice between a shell executor and its test command. The Apache-2.0-licensed [GitHub releases](https://github.com/acidkill/JevCompass/releases) contain a reviewed local catalog, two default nonblocking Codex hooks, optional OpenRouter Decisions ranking, explicit recommendations, an installer, and diagnostics. PyPI v0.1.17 added explicit custom-skill curation; published v0.1.18 corrects its privacy disclosure and the four-document release gate is enforced in the existing CI job. Published 0.1.20 suppresses the generic singleton shell for package documentation after the installed 0.1.19 P05 pair tied on blind README quality. Published 0.1.19 locally filters Python test runner choices using unambiguous CI commands after 0.1.18 remotely selected pytest for a unittest-gated repository; its exact-tag Python suite, distribution check and clean registry pipx install passed. Registration requires a preview and approval of generic fields before they may be sent to OpenRouter. The bundled coding skills and agent-spawn advice remain opt-in. Neither macOS runtime nor a repeatable speed or quality gain is verified. The first four synthetic CLI pairs tied on blind quality; later focused evidence was mixed. See [PILOT.md](PILOT.md) for observations and [TASKS.md](TASKS.md) for task/commit tracking.

## Efficiency experiments

The supplemental P09 comparison exposed an exact-CI measurement gap. Earlier substring receipts cannot prove exact or equivalent checks. The corrected parser safely unwraps the observed Codex `bash -lc` form; a fresh pair had treatment execute exact CI while baseline executed the same unittest suite without verbosity. Treatment was slower (55.60 versus 29.38 s), and a completed strict exact-command pair remains open. Reduce redundant skill overhead and repeat pairs before an efficiency claim. [PILOT.md](PILOT.md) records both paired receipts.

The source advisor now skips redundant testing advice when a coding prompt prescribes an exact runner, and offers unittest for Python code changes only with unambiguous local unittest CI. A P01 negative control with silent treatment passed quality and checks in both arms; 16.97 s treatment versus 22.24 s baseline cannot establish advice benefit. Next run advised pairs without a prescribed command and compare completion time, quality and required checks; see [PILOT.md](PILOT.md).

A fresh randomized pair of completed simple P01/P03 tasks with equal bundled skills found P01 treatment slower despite local advice (20.60 versus 13.79 seconds), and P03 treatment faster without advice (15.57 versus 18.10 seconds). Both arms passed blind source quality and their required commands. More balanced, advised pairs with first productive action and remote overhead are needed before an efficiency claim; see [PILOT.md](PILOT.md).

The opt-in compact-advice trial reduced one synthetic context from 780 to 616 characters but its one P01 treatment arm took 21.24 s versus 18.50 s baseline with identical blind quality and passing unittest. Keep the published default; repeat advice-versus-advice and baseline pairs across tasks before considering shorter context. Details: [PILOT.md](PILOT.md).

## Efficacy study: 20 matched cases

Design eight planning tasks, six subagent tasks, and six routine controls spanning Desktop and CLI where feasible. Run randomized equivalent baseline/advisor arms with the same model/settings and freeze blind quality scores before opening diagnostic arm mappings. For each case, assess advice relevance and availability, required checks, blocks, data minimization, and time to the first **productive** action. Compare paired outcomes and collect safe latency metrics. The first four synthetic CLI pairs tied in blind quality; later focused results were mixed. A 0.1.19 P01 pair had a post-unblind scoring correction and missing required-test receipts, so it cannot establish blinded efficacy. The subsequent CLI pilot parser separates recognized test invocations and completions from an observed exit for future pairs; old receipts cannot be retroactively resolved. In one fresh repeat, both anonymous helper artifacts passed the predeclared quality rubric; after mapping, treatment had a recognized successful unittest while baseline test execution remained unobserved. This single local-advice pair does not establish causality or the acceptance thresholds. A separate installed-0.1.22 **CLI surrogate** for the Desktop-assigned P08 project-scaffold case produced a blind authored-package quality tie; treatment reported local `exec_command`/`git` advice before first tool (8.11 ms). It does not count as Desktop coverage and the old receipt omitted observed test exit. A first repeat recorded unittest start/completion but its receipt allowlist dropped the exit result; the allowlist has been corrected and tested. A further blinded installed-v0.1.22 CLI pair tied on package quality and retained a recognized successful unittest in both arms (score SHA `d438a219...`, treatment local advice 10.46 ms). These small CLI surrogate trials show preserved checks in that pair, without a measured improvement or Desktop coverage. A corrected installed-0.1.22 P07 write-task pair was blind-scored before arm mapping (score SHA-256 `345043089f5c087f98f3beb28a148959ce261fa46b754bf675e08193ab754b41`): baseline produced a coherent API contract and treatment had no authored file. Treatment abstained with `api-design/insufficient-candidates` at 5.67 ms, so the quality difference cannot be attributed to Jev advice. First productive action and other acceptance ratings remained unscored. A fresh installed 0.1.20 CLI P05 smoke confirmed `low-signal-skip` and no agent-visible advice before first tool, while a routine help check exited 0. It does not measure speed or quality. A separate installed 0.1.19 P05 documentation pair tied on blind README quality; treatment's only listed candidate was generic `exec_command`, and its test failed in the fixture while baseline test execution was unobserved. First productive action stayed unscored, so do not infer a speed effect. The sample remains small.

Adoption targets: zero blocks or disclosures; zero omitted required checks; at least 80% useful advice; at least 90% coverage of eligible events; remote Jev p95 below two seconds; and better time to first productive action. If remote selection does not help, keep the local catalog and explicit command while disabling automatic remote choice. Count manual `recommend` trials separately. Do not infer a task from the unsupported default-role subagent transcript or silently change Codex's permission policy.

## Faster and cheaper coding: measurement before claims

The next pilot must include simple, bounded tasks (for example a small Python helper and a one-defect shell fix) in both baseline and JevCompass arms, and measure elapsed time through full task completion for each arm. It should compare matched coding tasks with the same Codex model, settings, synthetic fixture and required checks. Record per-arm total Codex process elapsed time and numeric root-turn `turn.completed` token usage from the Codex CLI when supplied, including cached input separately. The [official event schema](https://github.com/openai/codex/blob/main/sdk/typescript/src/events.ts) defines usage for a turn; it does not cover separate turns or child agents. Cached input is included within input, and reasoning output within output, so do not double count either. Score authored output and test preservation blindly before mapping. Treat first productive action as a separate human rating; first tool or first source read is only a timing proxy. For remote Jev, record its decision latency and request count separately, then include that overhead in the task comparison. Token counts are a cost proxy, not a currency estimate; actual prices and billing vary by model, cache and provider. If usage is missing or malformed, leave that pair's token comparison unscored.

A candidate improvement must shorten time or reduce comparable uncached input/output usage **without** degrading blind quality or skipping required tests across repeated relevant pairs. Prefer local selection and cached safe category choices when remote ranking has no competing candidates; keep routine controls silent. A single faster arm is model variation, not proof. Publish no cost-saving or speed claim until the paired results support it, including Desktop where the feature is advertised.

## Product candidates after measured results

1. **Better relevance:** use blinded negative cases to refine local classification and reviewed `use_when`/`avoid_when`. The opt-in spawn advisor is source-tested on one CLI child using a descriptive task name; run matched useful-action trials and Desktop coverage before considering default enablement. Keep generic-shell singleton abstention. A clean profile has no reviewed API-design skill and correctly stays silent there. A opt-in `jevcompass-api-contract` prototype was tested in two blinded P07 pairs and withheld: ambiguous wording gave two missing files despite treatment advice, while an explicit file request yielded a valid baseline contract and no treatment file despite local advice. The skill and catalog mapping were removed; only the clearer P07 test prompt remains. These small local-only pairs do not establish a causal effect or justify releasing the candidate. The optional two-skill prototype remains explicitly opt-in and experimental. v0.1.16 adds conditional matching-skill guidance from PR #63; a source-built C05 pair read `create-plan` but tied 6/7 on blind scores. This does not demonstrate speed or quality benefit. The installer ships as an explicit experimental opt-in after artifact and CI gates; require stronger task and Desktop evidence before recommending it broadly or enabling it by default. Never install a skill silently or claim that a configured MCP tool is callable.
2. **Coding workflow:** trial test ordering, error triage, and task priority based on coarse metadata with explicit criteria. Repository-required tests and real exit codes remain authoritative. Enable only after matched tasks show value and the data sent to Jev remains safe.
3. **Platform support:** document host-specific hook event schemas and trust behavior after macOS and Linux validation; keep Windows as a separately tracked idea, not a supported platform promise.
4. **Packaging and distribution:** production PyPI publication for `acidkill/JevCompass` completed through [workflow run 36114012972](https://github.com/acidkill/JevCompass/actions/runs/36114012972), using `pypi.yml` and the `pypi` environment, from tag commit `7e44137f3471532dfbf74d7a61c0e8946a58062f`. PyPI JSON reports wheel SHA-256 `b4331c437f1b193ffd50a3da60dcf6105e0cb50b6f085f4745f14cd5ec1bcd7a` and sdist SHA-256 `a066bef4c3fd700b938e1b9f705556d755a4d423e33a92a5653c4b6f22e27303`. A fresh isolated pipx install from the registry succeeded; `doctor` passed with the two default hooks and no `PreToolUse` gate. Continue to verify other Python versions and macOS separately before making those platform claims. TestPyPI remains a distinct `release.yml` workflow and `testpypi` environment with its own publisher and approval. The repository is licensed under Apache 2.0.
5. **Later integrations:** consider narrowly scoped permission-request advice or native Codex plugin packaging only if the advisor shows value. Any permission feature needs opt-in, separate privacy and regression tests, and must preserve Codex approval; do not restore broad `PreToolUse` gates.

Each feature moves into a release only with its own tests and host-visible evidence. JevCompass remains optional guidance, never an authority for permissions, skill use, or required validation.
